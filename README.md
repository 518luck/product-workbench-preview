# 产品蓝图

产品蓝图面向 AI 辅助开发，为人和 AI 建立一份共享的产品上下文。它通过 Skills 快速初始化一本产品书，让人看懂项目有哪些功能、各自有什么作用、业务如何运转，也让 AI 依据蓝图理解项目、更新已有功能或新增功能。

本工具的初始化方法面向不同项目。产品书中的名称、角色、功能数量、分组、规则和图表根据目标项目的源码与需求归纳；下面对三个 Skill 和本机工具的介绍，是本工具自身的能力，不是其他项目的固定功能目录。解析和验收能力仍以实际语言支持与环境边界为准。

在 AI 承担大量代码开发的过程中，用户需要从产品层面理解项目，并用自然语言表达变化。蓝图把产品知识从代码中提取出来，按业务能力组织，保存功能定义、规则、流程、异常、依赖和验收要求，作为后续开发可以持续读取和更新的上下文。

核心使用流程是：**初始化产品书 → 人阅读并用自然语言提出修改 → Skill 根据蓝图驱动 AI 开发 → 同步蓝图，让它持续反映产品。**

## 产品目标与分工

| 参与者或组成     | 在产品中的职责                                                        |
| ---------------- | --------------------------------------------------------------------- |
| 人               | 阅读产品功能和作用，用自然语言提出新增或修改需求，确认产品行为        |
| 产品蓝图         | 保存人与 AI 共享的产品认知，为项目理解、需求讨论和开发提供上下文      |
| 三个 Skill       | 引导 AI 初始化产品书、核验已有功能、按保存后的蓝图实现功能            |
| 固定 HTML 界面   | 面向人的阅读与编辑入口，展示产品内容和业务图表                        |
| CLI 与分析辅助层 | 为 Skill 提供读取、变更预览、校验、保存、源码分析和固定 HTML 生成能力 |

开发这个工具时，优先判断：产品书能否快捷建立、人能否看懂功能和作用、AI 能否据此准确新增或修改功能并同步蓝图。版本、验收和并发保护服务于这条协作流程。

用户可以在网页中用自然语言编辑功能定义，也可以在 AI 对话中提出需求。外部 AI 通过 Skill 执行后续整理和开发；网页与 CLI 本身不调用模型，页面保存也不会自动触发 AI。初始化和核验实际行为时，AI 仍需读取源码与配置；蓝图提供产品层面的入口，源码提供实际行为与实现依据。

## 工作流配置与独立发现

项目根目录 `.blueprint-workflow.json` 控制允许使用的 Skill 和初始化阶段。开启表示可执行本次明确任务，不会自动运行模型或其他 Skill。AI 负责读取和维护配置，用户可直接说“本次只测试全局发现”。

```json
{
  "version": 1,
  "skills": {
    "init": { "enabled": true, "stages": ["discover"] },
    "verify": { "enabled": false },
    "implement": { "enabled": false }
  }
}
```

本仓库采用以上配置，下一轮只测试业务发现。独立 discover 建全仓机器清单，读取相关入口与结果片段，保存候选业务目录及模块对账；不要求整仓逐函数记录，不生成或覆盖产品书，不启动服务。它的完成结论是 discovery-ready，initializationComplete、bookGenerated、runtimeVerified 始终为 false。候选目录仍需业务语义审阅，结构通过不表示任意项目业务已经理解正确。

目前只有 discover 可独立运行。analyze、compose 可与 discover 一起选择完整三阶段，沿用兼容流程；其他独立阶段组合会明确报告尚未实现，不偷偷退回全量执行。没有配置文件时保留原完整初始化默认值。分功能展开及独立合并仍是后续阶段。

工具入口：workflow get/set/plan，schema --workflow；独立发现输入见 schema --discovery，保存/恢复用 discovery record/check。配置保存使用当前 configHash 防覆盖，损坏配置拒绝执行；实现依赖的核验关闭时，计划在改代码之前阻止执行。这是产品工作流约定，不是宿主应用的 Skill 安装开关或操作系统权限控制；原有底层 CLI 命令仍保留，Skill 必须先检查计划。

开发评测可只选一个样例和 discover 阶段：scripts/evaluate-business.mjs 接受配置 {agent:{command,args},caseIds:["workflow-and-api"],stage:"discover",trials:1,timeoutMs:300000}。夹具和评分真值隔离，超时/仅声称成功都失败，报告保留耗时与产物；不会自动选模型。本阶段无需启动整本书初始化。

## 从产品书开始使用

在已安装对应 Skill 的 AI 会话中，按目标选择入口。以下目录和产品名称仅为示例：

| 目标             | 给 AI 的指令示例                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 理解已有项目     | `$product-blueprint-init 请为 /我的项目 直接生成产品书，梳理产品背景、功能和作用、业务规则与流程，完成后提供阅读入口。` |
| 建立新产品       | `$product-blueprint-init 根据以下需求建立产品蓝图草稿：……`                                                              |
| 核验已有功能     | `$product-blueprint-verify 核验当前产品书，让我选择全部功能或指定功能。`                                                |
| 落地确认后的功能 | `$product-blueprint-implement 按已确认并保存的定时关闭功能蓝图实现代码，执行验收并同步蓝图。`                           |

首次初始化默认在目标项目的 `.blueprint/` 生成产品 JSON 和 HTML，完成后自动启动本机编辑服务并打开页面，提供编辑链接、产品定位和核心旅程，用户先看产品书再提出修改。初始化使用 source 交付检查，按源码判断实现状态，不默认执行运行验收；用户可继续调用核验 Skill。dry-run 用于内部检查，不要求用户先确认陌生项目的内容；明确要求只预览时才停在预览。已有项目由初始化 Skill 读取源码并归纳产品书；新项目由需求建立草稿。已有目标蓝图时先读取并维护原内容，保留稳定编号、用户定义和历史；其他产品的示例文档保留。用户明确指定目录时遵循指定目录，已有产品书继续使用原路径。

新初始化的产物位置统一为：

- `.blueprint/`：产品定义 `product-document.json`、阅读页 `index.html`、最终交付审阅 `delivery-review.json`。
- `.blueprint-analysis/`：CLI 管理的分析会话与验收证据；AI 的中间批次、配置和辅助脚本放在其 `work/本次任务编号/` 下，简单输入直接走标准输入。
- 系统临时目录：运行副本、截图和安装文件。成功后清理本任务不再需要的工作文件，保留分析与验收证据。

三个 Skill 固定并显式传递同一文档路径，不在根目录或源码目录散放生成文件。此约定由 Skill 执行；CLI 仍支持显式指定其他文档位置，不自动搬迁已有数据。

阅读生成的 HTML 后，用户可以新增功能或用自然语言编辑已有定义；需要保存时通过本机服务打开页面。需求在页面中编辑定义或写批注并保存。核验 Skill 选择单个或全部功能，检查源码和实际运行结果；实现 Skill 选择单个或全部待办，落实保存后的修改并自动核验本次功能。用户已明确选择范围时不重复提问。

不熟悉定义时，在功能定义下方的“批注”中描述需要修改的内容，通过本机服务保存即可；已保存的批注可以逐条编辑、保存修改或删除。保存批注不改变定义或完成状态；调用实现 Skill 后，AI 会读取蓝图中的待实现定义和已保存批注，整理需求、修改代码、验收并同步蓝图，成功后删除对应批注，失败或未处理的批注保留。无需逐项复制指令。直接打开 HTML 是只读快照，浏览器暂存的批注尚未写入 JSON，Skill 无法读取；需要通过本机服务保存。页面不自动启动 AI。

三个 Skill 分别是初始化、核验和实现。初始化后可继续调用核验；实现后复用核验流程并沿用已选功能。需求由页面维护，不再单设需求维护 Skill。为本工具建立产品书时，三个协作入口分别定义；页面、CLI 等交付给用户的独立目标与结果仍须纳入对应分组。总旅程和 Skill 数量都不能决定整本产品书的功能数量。

初始化还要按实际依据整理图表：功能时序图说明交互顺序，数据流图说明输入、处理、存储和输出，项目架构图说明职责边界，数据关系图说明业务对象之间的包含、引用和版本关系。适用且有依据时默认生成，跳过时说明原因；图表字段可选不代表交付时可以全部省略。

用户绕过蓝图直接修改代码时，Skill 也会先运行 `document status`，比较当前源码与上次验收的内容指纹。即使没有草稿或批注，也会核对已完成功能受影响的情况；新提交不自动当作新功能，已实现且符合需求的代码只需核验并同步。完成登记通过分析会话自动保存源码基线，旧记录缺少基线时明确提示尚未核验。本机页面打开或点击“重新核验源码”可查看提示；独立 HTML 不检查实时源码。

代码变化后应同步蓝图中的实际规则、流程与依据，使下一次人或 AI 进入项目时能够沿用当前产品认知。初始化按实际实现判断状态：对照源码确认当前定义全部实现时显示完成；有明确未实现项时显示草稿并逐项列出缺失内容；无法判断时显示待确认。运行验收独立记录，不把未测试等同于未实现。

## 业务发现与规模

初始化先列出目标项目的真实操作，再按使用者、目标和结果建立业务地图。多个命令或路由共用一个函数时仍保留各自身份；内部 helper 不自动变成功能。地图在详细分析前形成，再沿源码及全部模块反查遗漏，不预设功能数量。

按文件读包减少重复正文，逐函数语义断言关联相关源码位置，保留完整读取和独立函数记录。新会话按行读取和事务保存；相同快照直接恢复，修改后仅复用未受影响且已核验的函数分析，并保留来源。机器索引在源码变更后仍会重建，业务结论与运行验收仍需重新核对。业务地图、实现情况与运行验收分别核对。新交付使用 v5；旧交付保留历史范围，不冒充已经通过新业务检查。四种语言共用业务操作与地图协议，自动入口规则按语言和框架声明；具体范围见 [ANALYSIS.md](ANALYSIS.md)。

业务发现评测独立于格式回归：`scripts/evaluate-business.mjs` 接入显式配置的外部 AI，在隔离项目按预设操作与结果评分；参考答案不写入模型输入。该评测不证明任意自然语言正确，实际业务审阅及更大项目盲测仍需分别记录。CLI和网页本身不调用模型。

## 分层验收与明确范围

完整理解源码不要求启动整个系统或穷尽所有内部分支。AI 先为每项业务保存验收方案，逐步骤选择源码核对、组件验收、契约两端验收或必要的端到端观测，再执行对应测试。组件与契约适合无法同时启动所有服务的项目；它们支持声明的业务断言，不等于整条链路已跑通。

分析记录还会跨单元检查职责模板；相同包装行为可以共享准确说明，不能给不同函数仅替换名称与源码前缀。机器检查仍不能保证自然语言业务解释正确。

职责与逐位置说明都会比较，无关编号、汉字标签和少量随机文字不能充当独立解释。不同业务步骤需要各自的行为依据和结果源码位置；同一返回位置换预期值或字段不能扩大步骤覆盖。异常验收要观察到实际拒绝或失败，自定义错误码可绑定同次调用的拒绝分支。交付审阅还会检查明确引用的项目文件是否存在；这些都是质量底线，不能代替对业务含义和预期结果独立性的审阅。

实现核对须把每个结论关联到具体行为位置或已读取的工作流原文；路径常量、重导出及单纯参数声明不能证明业务实现。组件和契约方案的 observations 逐项绑定单个 step 和 criterion，工具在临时副本中实际采集返回值、异常或分支并核对预期；成功日志、产品书完成标签、返回类型和普通命令退出零不能代替业务结果。JS/TS 结果可通过 JSON Pointer 核对具体自有数据字段，不执行 getter；其他语言的字段观测尚未提供。

源码对照确认当前定义已实现时可以完成，业务验收另行记录；完整系统联调不可用时，保留具体未核验边界。只有源码依据而没有运行证据时，写明已有实现、运行未核验。页面分别展示各层验收与业务步骤覆盖，几个辅助函数通过不能让整个功能显示“已核验”。

新交付使用 delivery v5，结论限于运行前保存的业务范围。漏读、浅记录、未归类入口、缺依据、遗漏方案、未执行场景或失败断言必须继续处理；只有与当前步骤有关的真实能力缺口或工具实际诊断的环境／外部障碍有证据且在页面可见时允许部分交付，仅读取说明文档不能代替诊断。旧 v3 审阅保留严格流程检查，历史完成记录不自动重写。CLI 操作由 AI 完成，具体协议见 [FLOW.md](FLOW.md)。

## CLI 与本机阅读入口

需要 Node.js 22.14 或更新版本，开发使用 pnpm。在工具源码目录运行：

```sh
pnpm install
pnpm blueprint --help
pnpm blueprint serve /我的项目/.blueprint --port 62040
```

`serve` 的路径应指向已生成的蓝图目录或 JSON 文件，打开终端输出的本机网址即可阅读和编辑。直接打开 HTML 可以阅读快照；使用 `render` 可以重新生成 HTML。

如果要手动创建文档容器，可运行：

```sh
pnpm blueprint init /我的项目/.blueprint --name "我的产品" --json
pnpm blueprint validate /我的项目/.blueprint --json
```

CLI 的 `init` 只创建空 JSON 文档和同目录的 `index.html`，不会覆盖已有文件。把源码或需求整理为产品书由初始化 Skill 中的 AI 完成。

本机安装后，以上命令的 `pnpm blueprint` 可替换为 `product-blueprint`。命令接受文档目录或 JSON 路径；具体读写规则见 [DOCUMENT.md](DOCUMENT.md)。

## 三个 Skill 与协作流程

| Skill                                                                      | 负责的工作                                                 |
| -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| [product-blueprint-init](skills/product-blueprint-init/SKILL.md)           | 读取源码、建立产品书与实现判断，检查后自动打开可编辑页面   |
| [product-blueprint-verify](skills/product-blueprint-verify/SKILL.md)       | 选择单个或全部功能，核对实现与真实运行结果，不修改业务代码 |
| [product-blueprint-implement](skills/product-blueprint-implement/SKILL.md) | 查找待实现定义及批注，实现验收后登记完成并清理已处理批注   |

三个 Skill 的文件夹可独立安装到 `$CODEX_HOME/skills`，未设置时使用 `~/.codex/skills`；安装前保留已有同名 Skill 的本机改动。安装后用 `$product-blueprint-init`、`$product-blueprint-verify`、`$product-blueprint-implement` 调用。

新增或修改功能时：人在页面保存定义或批注 → 调用实现 Skill 选择单个或全部待办 → AI 实现 → 自动调用核验流程核验所选功能 → 同步蓝图并清理本次已处理批注。核验也可独立调用，只记录实际结果，不自动修代码。功能完成表示定义已实现，草稿列明具体未实现内容；运行验收独立记录。

源码分析采用 v2 协议：JS/TS（含 JSX/TSX）使用固定的 TypeScript Compiler API，Python、Go、C++ 使用随包的 Tree-sitter WASM，并按本机能力补充 Python ast、Go packages/SSA 和 Clang 编译数据库语义分析。工具分别核验完整读取、逐位置分析、业务调用与数据绑定、声明场景的真实运行。语法解析不等于深度核验可用；当前运行探针的范围与限制见 [FLOW.md](FLOW.md)。旧浅摘要与旧执行记录保留为历史，不能直接复用新结论。

初始化交付使用 `document check --mode source`：完整源码分析、业务地图和排除审阅、实现判断、图表与 HTML 均须通过，但不要求运行验收。返回 `completion.claim:product-book-generated`，不能宣称功能已通过运行核验。运行验收由核验 Skill 执行，整本严格验收交付使用默认的 `--mode verified`。任何模式下 `completion.canDeliver:false` 都表示尚未交付，需按 nextAction 补齐；保存地图、实现标签或执行编号均不替代最终检查。用户现有定义、批注和验收历史不自动改写。

实际验收可用 `verification run ID /文档 --analysis-session SESSION --input 命令.json` 显式执行命令，获取 `executionId`；完成批次带 `--require-verification` 核对文档、功能、定义及源码版本。静态扫描与网页仍不执行项目代码；只有显式验收命令执行调用方提供的检查。退出成功不能证明检查覆盖全部业务，需要实际正常与异常路径。

开发中的真实 AI 初始化评测入口是 `node scripts/evaluate-init.mjs --agent 运行配置.json --trials 3`。配置为 `{ "command": "codex", "args": ["exec", "--ephemeral", "--sandbox", "workspace-write", "--skip-git-repo-check", "--json", "-"] }`，也可传其他支持 stdin 提示的本机 AI 命令；模型使用调用方配置，不自动替换。六个场景覆盖已有功能完成、未实现需求草稿、示例保护、嵌套源码、中断恢复和批注协作闭环，外部 AI 每轮默认时限为 20 分钟，可用 --timeout-ms 调整；每次在新临时目录运行，以实际产物独立评分，保留报告与执行记录。`--case implemented --trials 3` 可单测场景。运行会调用外部 AI 并消耗其额度；普通 `pnpm check` 只测试工具和评分器，不运行模型。小样本结果不能作为任意项目的稳定性保证。

评测脚本的默认时限用于隔离的微型样例，不是大型仓库初始化的耗时承诺。实际成本随函数、审阅位置、业务复杂度和模型速度增加。分析采用批量读取与增量保存；已有实现的功能验收、严格流程追踪和交付审阅分别推进。

## 项目结构

| 位置        | 用途                                           |
| ----------- | ---------------------------------------------- |
| `assets/`   | 固定界面的黑白主题、目录、表单和图表布局       |
| `lib/`      | 校验、源码分析、文档操作、保存、服务和模板组装 |
| `bin/`      | CLI 入口                                       |
| `schema/`   | 文档、整批变更和分析的 JSON Schema             |
| `skills/`   | 三个 Skill 及其参考流程                        |
| `examples/` | 通用最小文档                                   |
| `test/`     | 使用临时项目和随机本机端口的回归测试           |

各项目的 `product-document.json` 是权威业务文档，同目录的 `index.html` 是生成快照，项目内的 `.blueprint-analysis/` 保存分析会话。本仓库的通用格式示例位于 `examples/`。AI 维护语义数据，HTML 始终由固定模板生成。业务内容与模板的约束见 [DOCUMENT.md](DOCUMENT.md)。

## 本机安装与开发检查

```sh
pnpm check
pnpm format:check
pnpm package:check
pnpm pack --pack-destination /你的输出目录
pnpm add --global /你的输出目录/product-blueprint-0.13.0.tgz
product-blueprint --help
```

也可通过绝对路径运行入口：`node /工具目录/bin/product-blueprint.mjs --help`。

可选 Go 语义工具由 AI 按需准备；基础 WASM 语法资源随包提供，运行不依赖 CDN。工具包采用文件白名单，包含程序、模板、规范、Skill 和通用示例，排除用户文档、生成快照、分析会话及测试。当前仅本机交付，保留 `private: true`，不发布包、不修改 shell 配置；尚未提供 MCP。

分层交付审阅 v4 从核心用户旅程检查功能与步骤覆盖，并要求规则、步骤依赖、业务验收条件及正常／异常路径的真实执行映射。失败时序须有实际分支，替代图表须存在。旧产品书继续可读，旧审阅重新核对后才能通过新门槛；工具不能自动判断产品含义或测试断言是否充分。

扫描报告的 scopeCoverage 会将声明范围与同一项目根目录的默认源码清单比较。过滤掉自有源码时，范围内读取完整不代表整个项目完整；默认初始化补齐遗漏。用户确实要求局部分析时保留原文、遗漏清单和范围说明，最多按该范围部分交付。工具记录范围声明，不能验证引用是否确实来自人类。

普通验收命令也在临时项目副本运行，并检查副本源码与定义是否变化；副本不是操作系统沙箱，绝对路径和外部服务仍需遵守授权。交付检查会报告当前扫描后新增的目录外杂项文件；它不推断扫描前文件的所有权，也不会自动删除用户文件。
