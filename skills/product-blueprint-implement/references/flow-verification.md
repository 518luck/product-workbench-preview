# 业务流程核验

使用分析协议 v2 和分层交付审阅 v5。先按 [分层验收](layered-verification.md) 保存业务范围方案；本篇用于被选择的端到端流程观测，不强制所有组件都做全系统联调。先查询 `analysis capabilities`、`schema --flow`、`schema --verification`，不要从版本号猜协议。CLI 操作由 AI 执行。

功能验收与严格流程核验独立推进：初始化或实现先以当前源码、字段依据和真实业务断言完成可独立验收的功能，再按下文补齐流程追踪。未核验连接和分支保留在流程状态中；不用等待全书追踪穷尽后才登记任何完成功能。需求维护仍不登记新的完成。

## 扫描、恢复与语言环境

扫描范围覆盖目标内自有源码。用 `contexts` 显式列出相关 Skill、工作流、HTML/CSS 与配置；它们有独立读取范围及内容哈希，不计入函数数量。核对默认排除项，生成的产品书和分析产物不加入上下文。

同一会话由一个写入者协调，优先使用 analysis read --input 的 reads 批次和 analysis record 的 records 批次；完整的父函数凭据可供内层函数独立记录引用。保留返回的结构化编号，避免并行进程争锁和手抄 ID。批量读取只优化执行，不替代逐项理解。

工具拒绝已识别的机械模板及带“调用／返回”前缀的源码复制；通过仅表示质量底线，不证明解释正确。必须实际逐项理解，不能换一套套话绕过。

去除源码片段和通用过程措辞后仍须有行为解释；换一套模板前缀不能代替理解。scan／check 的 scopeCoverage 另列自有源码遗漏，默认补齐而不缩小范围。

`recordedCount` 只表示已保存；`reviewedCount`、完整读取凭据及claims／旧 coverage 检查通过才表示分析合格。长函数读完所有分段；嵌套函数独立记录。恢复先执行当前 `analysis check`。源码、解析器、分析规则或上下文变化后重新扫描，旧记录只作历史，不搬旧摘要、凭据或旧 valid 报告。

JS/TS 使用 TypeScript Compiler API；Python、Go、C++ 先用随包的 Tree-sitter WASM 解析，再按 capabilities 使用本机 Python ast、可选 Go packages/SSA、Clang 编译数据库。Go 工具需要时由 AI 执行 `analysis prepare --language go`，C++ 深度工具使用 `analysis prepare --language cpp`；缺少 LLVM 开发库时先准备环境。缺依赖时先在授权范围准备，不能只因尚未安装就结束；无法准备时保留具体环境缺口。动态调用、装饰器、接口、反射、宏、虚调用和指针不由名称确认。当前运行探针的支持范围以工具返回的 unsupported 为准；语法覆盖不等于深度核验可用。

## 建立业务映射

定义保存后分页读取 entries、values、edges 与相关 units。入口按真实导出／注册身份识别，嵌套函数仍须分析，但不会继承外层的导出身份。当前且绑定同一产品书的验收方案／流程步骤会关联实际引用的入口，并沿机器确认的调用及词法回调归类内部可达入口；无需为此运行全系统。剩余入口须关联业务，或为已完整分析的非业务库导出／声明保存 dispositions:[{entryId,kind:"non-business",reason:"指出具体函数或文件及非业务职责"}]。CLI、事件注册和 Skill 工作流入口不能用这种方式排除；旧的仅 reason 说明不能消除缺口。核心旅程仍从项目材料独立核对，入口清单和源码可达不证明全部业务或运行通过。

用 `flow record /产品书 --session SESSION --input 映射.json` 保存：

- 每个流程绑定真实 entryId，步骤绑定 featureId、从 0 开始的 step 与 unitId／contextId；输入输出引用机器生成的 data fact ID，规则、异常及持久化位置放在 pointIds 或相关单元中。
- 连接引用当前机器生成的 callId、sourceId、targetId；调用编号使用完整起止位置，链式调用不能手抄或复用旧编号。转换是明确的处理步骤；同名字段、相同常量、看似相同的值都不是数据衔接依据。不要省略参数映射或返回结果。
- 场景从实际入口到结果，覆盖正常与适用失败路径，声明连接和可观测断言。不能仅声明“命令成功”。

执行 `flow check`，按具体 gap 修正映射或补充证据。文字解释、手写日志、随意清空 unknown 或改变入口排除说明不能将未知连接升级为通过。

## 真实运行

`verification run` 输入携带 `flow:{id,scenarioId}` 才收集流程证据。CLI 在临时副本校验业务源码后注入自己的探针；`fixtures` 只新增夹具，不能覆盖原文件；`setup` 用于准备，`build` 在注入后编译。编译、执行不改变原项目；准备或运行修改副本业务源码时证据失效。普通验收命令仍可用，但退出成功不证明业务连接。

探针通过独立通道采集真实函数进入、参数传递、返回、异常及结果。同一次调用与请求分别关联，不能拼接不同运行。先执行适用场景，再运行 `flow check`；`verification run valid:true` 本身不是流程已核验。

浏览器场景使用 `browser:true`，命令在副本启动本机服务并输出一行 `{"url":"http://127.0.0.1:实际端口/"}`。运行工具保持进行时，读取 browserReady 返回的代理网址，用宿主浏览器实际交互，结束时点击“结束本次流程采集”。页面探针向本机采集器提交事件；无法执行宿主交互则保留缺口。跨浏览器／服务器、网络、消息和 Skill 宿主连接没有专门传输证据时仍为未核验，不把两端日志拼接。

## 同步与交付

`flow sync /产品书 --session SESSION` 保存工具计算的状态并重新生成 HTML。流程“已核验／部分核验／未核验／失败／已过期”与功能实现情况“草稿／完成／待确认”分开；保留已有完成历史，不因其他流程缺口一律改草稿。源码、定义、步骤内容、探针或核验器变化会使相应绑定失效。

初始化或实现流程先按当前产品源码、字段依据和真实业务断言登记可独立验收的功能，再逐步补齐严格流程追踪；函数已实现并验收，不因尚未采集所有连接或分支而一律保留草稿。普通执行不证明流程通过，带 flow 的执行仍须满足流程检查。若有整体语言／语义／适配缺口，独立完成还要求工具确认它们全部在本功能核验范围外；漏读、漏记录和缺少本次验收的字段依据继续补齐。需求维护仍不登记新的完成；整体缺口和严格交付结论分别保留。

交付审阅 v5 的 flows 引用本次选择严格核验的真实映射；acknowledgedGaps 按检查结果的 kind、path（无 path 时用 flowId、entryId 或 `/`）说明具体影响。先修复漏读、漏记录、漏映射等可解决问题；只有真实语言／环境／宿主能力限制且有分层方案中的证据才允许部分交付；漏做的场景不能仅填写理由便结束。`document check` 的 valid 是严格结论；deliverable 为 true、stage 为 partial 仅表示产品书可读且缺口完整可见，不能称严格通过。结论限定为已识别入口、声明场景及当前支持范围。

部分交付也自动启动 serve、核对保存能力并打开页面，最终仍以链接、产品定位和核心旅程交付；必要时仅加一句未核验范围说明。技术凭据和缺口留在产品书与记录中，不转交用户执行命令。
