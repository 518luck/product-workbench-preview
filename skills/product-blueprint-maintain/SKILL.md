# 维护需求与蓝图

将用户需求和源码变化整理到现有产品书，保留用户原文、稳定编号与历史。本流程可在更新文档后结束，不默认进入代码实现。

业务内容由目标项目决定：从该项目的使用者、入口、业务对象、规则和结果归纳功能，名称、数量、分组和流程不预设。本工具的三个 Skill 是协作入口，只有目标产品本身提供这些业务时才纳入其功能清单。

本流程中的 CLI 操作由 AI 在授权范围内直接执行，交付页面链接和处理结果，不要求用户复制命令或打开终端代为操作。遇到工具、环境或权限阻碍时先排查，无法解决时说明具体阻碍及需要的授权，不把执行任务转交用户。用户主动询问命令用法时再提供命令。

发现新增或变化的业务入口时，先按 [业务发现与核对](references/business-discovery.md) 更新操作与业务地图，再展开源码；沿用未变化的业务和稳定编号。

开始前读取 [产物目录](references/artifacts.md)，固定产品书、分析记录和本次工作文件的位置；首次生成默认使用目标项目的 `.blueprint/`，已有产品书继续使用原路径。

## 工作流程

1. 读取产品背景、相关功能与依赖，确定本次需求和授权范围。文档位置不清楚时先定位，不创建另一份蓝图代替现有内容。
2. 运行 `document status`，核对当前源码与已有验收基线；已完成功能没有批注时也检查代码变化。按 [维护流程](references/workflow.md) 读取相关材料并完成当前分析范围的记录。
3. 区分代码已有行为与未来需求，整理规则、流程、依赖和受影响功能。保留原始定义；只有用户明确要求改写时才修改定义原文。
4. 用明确变更批次做 dry-run，展示业务差异、受影响范围和待确认问题。确认后提交；已有授权明确覆盖相同变更时直接继续，不重复确认。只要求预览时不保存。
5. 读回保存结果并生成 HTML，交付阅读链接与简短变更说明。尚有歧义或缺口时说明具体影响。

选择验收范围和执行方式时读取 [分层验收](references/layered-verification.md)，先保存逐业务步骤方案，再执行组件、契约或必要的端到端验证。源码完整分析与全系统联调分开；选择端到端验证时再读取 [业务流程核验](references/flow-verification.md)。核对每个验收结果确实支持对应业务，不能为了通过而替换实现来源或缩弱断言。候选入口按当前业务步骤归类；漏读、机械摘要、漏记录、未归类入口和未执行的声明场景继续补齐，只有真实限制才允许明确部分交付。

实现状态按 [实现情况与验收情况](references/implementation-status.md) 判断：完成表示定义已实现，草稿必须列明实际未实现项；未能判断时标待确认。运行验收另行记录，不能用未测试代替未实现。

## 必须保留的边界

- 不实现项目代码、不登记新完成记录、不清理待实现批注。可在临时副本核验本次声明场景，流程检查不改写已有完成历史。
- 源码变化提示待核验，不自动修改定义版本或用新指纹覆盖旧验收基线。业务变化使旧实现结论转为待确认；改名和分组不改变完成状态。
- 用 CLI 保存最小明确变更，保留未指定字段、备注和历史。删除功能或改写原文须有相应授权。
- 需求明确但尚未实现时记录为期望行为；缺少证据不能写成已实现事实。
