# 实现情况与验收情况

完成表示当前功能定义已经实现；草稿表示有明确尚未实现的内容。测试未运行、未覆盖全部分支、没有追踪证据，不是未实现的证明。无法判断实际实现时使用待确认，不猜测完成，也不混入草稿。

## 按定义核对实现

初始化和实现 Skill 在保存定义后，读取 `schema --assessment`，使用 `feature assess ID BOOK --analysis-session SESSION --input 核对.json --json`。输入包含 expectedHash、当前 revision 和 items；可先 dry-run。需求维护仅更新定义和业务影响，不调用此命令新增完成结论。

items 逐项覆盖 `/description`、每条 `/rules/N`、每条 `/checks/N` 和每个 `/flow/N`，N 从 0 开始。每项包含：

- target：实际业务位置。
- state：implemented、missing 或 unknown。
- detail：具体实现行为、尚未实现的内容，或无法确认的实际原因。
- unitIds／contextIds：当前会话中已完整读取并分析的产品源码或上下文编号。已实现和未实现判断均需依据；纯需求且没有产品源码的项目，可为 missing 提供 requirement:{source:user|document,text:需求原文}，它不能证明实现完成；测试辅助源码不能代替产品实现。

每项还需 basis：代码使用 {kind:"code",unitId,pointIds:[本单元实际位置编号],detail:具体关系说明}；工作流等上下文使用 {kind:"context",contextId,quote:实际原文,detail:具体关系说明}。上下文必须完整读取且引文匹配。unitIds／contextIds 可由 basis 派生，显式提供时须包含全部来源。引用真正执行行为的函数及位置；包路径、重导出和参数声明不能证明功能，说明不能仅换一种说法重复定义。

每条 detail 和 basis.detail 解释所引行为、条件及结果如何满足当前这一项定义；不能将“核心函数已实现对应逻辑、维护状态一致性”复制到所有规则和步骤。文件名、函数名和源码片段本身不构成说明。共享辅助函数只有实际支持本项行为时才能引用，流程映射不能用另一批无关单元替换实现核对来源。

不同业务步骤各自引用独立行为位置；共享辅助函数可作补充，但不能给所有步骤只贴同一个输出点或整段工作流原文。重复调用同一辅助函数时，引用各步骤实际调用点。核对失败应回到业务实现补足位置，不能换成更容易测的函数；实现不确定与确实缺失分别记录。

根据实际业务逐项解释，不能只抄函数名或说“文件存在”。Skill 的指令与资源也是产品实现的一部分，应对照目标、步骤、权限边界和交付行为判断；是否实际执行过相关 AI 场景单独记录。

工具计算状态：全部 implemented 为完成；出现 missing 为草稿，页面逐项显示未实现内容；没有 missing 但存在 unknown 为待确认。旧文档没有当前实现核对或有效完成历史时显示待确认，不推断具体未实现项。定义变化使旧核对失效，需要重新对照；改名和调整分组保留结论。

missing 说明具体业务缺失，例如“尚未在删除批注时检查编辑版本”；不能写“未跑测试”“未复跑所有分支”。同一功能既有明确缺失又有未知时，分别记录。源码变化后重新分析并核对，不能只刷新指纹。

## 验收独立记录

实现核对保存当前源码基线和核对历史，不生成 executionId、不写测试通过、不删除批注。完整源码读取、业务字段依据与验收交付检查仍须执行；实现完成不等于严格验收通过。

按分层方案运行已声明场景。失败若揭示业务行为确实缺失或错误，修复后重新核对；无法运行则具体说明未验证范围和真实障碍，不能反过来编造缺失功能。源码已明确实现时，完成状态可以与运行未核验同时存在。

`feature.complete` 保留为真实验收登记与已处理批注的原子清理入口，带 require-verification；有未实现或待确认核对项时先对照实际代码更新核对，不用测试记录覆盖它们。只有本次确实实现并验收通过的批注才能清理。

本次实际使用只有触发目标产品的相应业务并观察到结果，才是该业务的使用材料；为项目生成产品书本身不算运行该项目的业务。当目标产品本身提供 Skill 或其他协作工作流时，按实际触发的入口、产物和结果记录本次场景，未执行的其他场景另列未验证范围，不能推断对应业务尚未实现。
