# 从产品入口审阅内容

初始化的成果应让人知道如何使用产品，也让 AI 知道要改哪些行为。读取覆盖和命令退出成功之后，还要做以下审阅。业务文档格式保持兼容，初始化使用 `schema --delivery` v5 和 source 检查，运行验收留给独立核验 Skill。

## 核心旅程与功能覆盖

从 README、实际用户入口及项目提供的工作流识别核心旅程，按发生顺序映射到功能和业务步骤，明确最终结果及材料依据。逐一对照这些旅程有没有遗漏能力；工具函数、测试辅助、扫描或验收机制不能代替产品核心工作流。

区分业务分组、独立功能和端到端旅程：用户能分别发起、目标或交付结果不同，或授权边界与停止条件不同的入口，应有各自的功能定义、流程、规则和验收。共用文档或出现在同一生命周期中不构成合并理由；总旅程用于概览，不能代替这些功能。功能名称、数量和分组由目标项目的实际业务决定，不按文件数、命令数、Skill 数量或本工具的功能清单凑数。目标产品有多个可独立结束的工作流时分别建模，不因同属一个生命周期便合并或强行顺序执行。

先建立“使用者与触发入口 → 输入和业务对象 → 关键规则与分支 → 结果或状态变化”的业务清单，再归纳分组与功能。对照页面、API、命令、任务和文档工作流反查覆盖，避免只看某类入口或内部模块。基础设施作为对应流程的规则和依赖；目标项目确实将其作为可独立使用的能力时再单独建模。

目标项目通过 Skill、脚本或文档提供业务工作流时，也读取这些材料，说明参与者、启动方式、产物及权限边界。仅用于开发该项目的辅助 Skill 不自动成为其产品业务。本工具自身的初始化、核验和实现流程，不作为其他目标项目的默认业务。

项目架构需要表达旅程中的主要使用与执行关系，尤其是谁阅读、谁修改目标数据或代码。每条关系都要有项目材料或实现依据，不能只画工具内部调用。自动检查能验证步骤映射，核心旅程是否覆盖实际产品仍需逐项审阅。

## 规则、依赖及验收条件

把实现中已知的业务约束列入 `rules`，并关联受约束的 `stepDetails.rules`；不要把约束全部埋在长描述里。功能级依赖关联实际使用它的步骤，不为了去掉空状态而给每个步骤复制全部依赖。纯展示或转换确实没有额外约束、没有依赖时可以为空，交付审阅的 `content.rules`／`content.dependencies` 填 skipped 并说明具体理由；已有内容填 included。

完成功能的 `checks` 写可判断的行为条件，例如“保存批注后原文可读，完成状态不变”和“旧版本写入冲突且保留输入”，而不是只写 `pnpm check`。未实现需求保留期望验收条件，不能填 passed。

`acceptance` 将每个验收条件映射到实际步骤及 normal／exception 情景，并引用本功能已验证的 executionId。`criterion` 是 checks 数组序号，`steps` 是 flow 数组序号，均从 0 开始。`evidence` 指明具体测试文件与用例、命令中的断言或实际交互记录，说明检查了什么。覆盖所有条件和正常步骤；已定义的异常步骤还需异常验收。只在时序 error 分支出现的步骤按异常路径验收，不伪造正常覆盖。没有异常时 stepDetails.exception 留空，不写“无异常”来凑字段。

同一个执行记录可以支持多个条件，无须为每个条件重跑整套测试。全量回归可用，但需要核对实际用例是否覆盖功能。页面保存、冲突恢复、图表切换等能力按项目约定实际验证交互；Skill 的自主行为用隔离项目执行相应工作流。命令成功和模型声称成功不能替代这些检查。

运行核验阶段再逐条对照“条件要求的行为 → 实际断言／交互 → 执行记录”，然后才关联步骤。文件和引用存在、打包资源齐全、未内置模型调用，只能支持资源与边界检查，不能支持 AI 整理需求、修改代码或验收同步。手写 CLI 批次与预先写好的代码夹具证明工具协议，不能当作模型调用 Skill 的行为验收。后续核验范围包含自主协作行为时分别实际运行对应 Skill；仅验证资源时明确缩小声明范围，不能通过挑选较弱条件来把整条业务标为完成。

## 最后核对

- 时序图的 failure 命名必须对应实际 error 消息，说明失败如何返回及如何保留或恢复用户内容；没有依据时不生成虚假的失败场景。
- 跳过理由不能互相循环。如果另一张图已充分表达，填写 decision 的 alternative 引用真实已生成图表；替代图也被跳过时重新判断。
- delivery-review.json 绑定最终文档哈希，包含核心 journeys、逐功能 content 与 acceptance，以及原有状态和图表判断。先读取当前 schema，不沿用 v1 审阅。
- 用浏览器核对实际正常／失败场景和详情。document check 通过后仍审阅核心旅程与架构的业务含义；检查器不理解自然语言，也不能证明 evidence 所说的断言确实充分。

交付失败时修复生成内容或补做验收，不伪造映射来消除提示，不因为旧审阅失效而重写现有用户文档。已有产品书仍可阅读，重新严格交付需要重新审阅。

完成状态不能靠隐藏未知项获得。业务实现有推断／未知时标为待确认；运行验收未完成单独记录，不推断业务尚未实现；纯边界说明且不影响当前已核验定义的 notes 可在 analysis trace 标记 completionImpact:informational，并用 note 说明为何不影响验收。省略仍按 blocking 处理；informational 不能用于 description、规则、流程、验收条件或替代 observed 完成依据。

建模后做双向核对：从每个实际用户目标和入口检查其结果、规则、正常与异常路径是否落到功能及步骤；再从每项定义反查相关实现位置和真实业务断言。功能少可能合理，不能按数量判合格；有独立目标却被合并或漏掉时按该项目实际业务补齐，不套本工具的清单。

交付 evidence 中声称存在的项目文件必须真实存在于项目范围；使用实际路径，外部网址只作补充材料。检查器能核对明确文件引用，但文件存在不代表行为结论正确。非业务入口排除须逐项说明职责与排除理由，不为所有导出函数套同一句“内部公共能力”。
