# 验收与交付检查

## 按功能判断实际状态

读回保存后的定义版本与流程，对照产品源码和实际验收条件逐项判断：

| 情况                                           | 处理                                       |
| ---------------------------------------------- | ------------------------------------------ |
| 已有实现与当前定义一致、流程完整且实际核验通过 | 同步流程并登记当前版本完成                 |
| 新需求或代码缺少具体行为                       | 保留草稿，记录缺少的步骤／规则和查找依据   |
| 已有实现，但验收失败或环境无法核验             | 保留草稿，记录具体检查、失败证据或环境障碍 |

首次整理不表示尚未实现；未核验也不等于未实现。不用同一段分析进度备注代替逐功能判断。

完成必须有当前分析快照的有效 `observed` 产品源码依据、与定义一致的已保存流程及真实业务断言；需求、资源存在和测试文件不能单独证明产品已实现。本功能漏读、漏记录或缺少支撑当前验收的字段依据时继续补齐。若工具确认剩余语言／语义／适配能力缺口全部位于本功能核验范围外，可根据独立真实执行登记完成；保留整体缺口，不声称全书严格通过，也不使用 `--allow-partial-analysis` 绕过门禁。与已核验业务无关的宿主未知项按 [内容审阅](content-review.md) 保留并说明，不自动判定所有功能未实现。

## 执行验收并登记完成

先读 `verification run --help`、`schema --verification` 和 `schema --changes`，按目标项目选择合适的现有测试、命令及界面交互。每个业务条件应有正常与适用异常路径的实际断言；同一执行记录可支持多个条件，无须逐条件重跑整套回归。

1. 保存业务定义与完整流程，再确认本次目标 revision。若流程已与定义一致，可用 `feature.sync` 声明同步；该操作不会生成流程。
2. 在当前源码快照下，通过以下命令实际运行验收。输入按 Schema 提供命令和参数，不经过 shell；超时等限制以当前帮助为准。

   ```sh
   product-blueprint verification run ID /文档 --analysis-session SESSION --input 命令.json --json
   ```

3. 只有返回 `valid:true` 才引用 `executionId`。将具体行为条件及对应编号写入 `implementation.checks`；`verifiedAt` 不早于实际执行结束时间，可选提交号也须真实取得。
4. 读回 revision 和 documentHash，使用独立后续批次提交 `feature.sync`／`feature.complete`，预检和保存均带 `--require-verification --analysis-session SESSION`。完成批次不携带业务修改或 `affectedFeatureIds`，避免递增刚验收的版本。
5. 工具自动将当前源码指纹、范围及清单写入 `implementation.sourceSnapshot`。不手填基线，不复用其他文档、功能、版本或快照的执行记录。源码或定义改变后重新分析并验收。

失败、超时或被修改的执行结果不能支持完成；旧手动记录保留但不冒充真实执行。命令通过只证明执行结果，仍须审阅断言是否覆盖业务。文件存在和协议夹具不能替代真实 AI 协作验收。

随后按 [业务流程核验](flow-verification.md) 建立调用与数据映射，运行声明场景并 flow check、flow sync。普通验收只支持具体检查过的功能行为，不证明所有连接和分支均被追踪；带 flow 的执行还须满足对应流程核验才能引用。功能完成与流程核验分开，不要求先穷尽全书流程的每个条件再登记任何完成功能，也不将缺少流程追踪解释为代码尚未实现。严格交付仍要求相应流程证据；不能用普通命令成功冒充流程通过。

## 最终交付检查

先确认当前 `analysis check` 的读取、逐函数位置说明和业务依据均有效；有存储记录或旧的 valid 报告不能代替本次检查。再从各功能规则及异常反查实现函数，确认条件、调用后果和失败顺序与分析、图表一致，不能仅凭位置计数宣称理解完整。

1. 运行 `document status /文档 --json`，确认本次已核验功能为 `current`。旧记录缺少基线时是 `unverified`；路径或读取问题需如实保留。
2. 用浏览器核验实际 HTML 的流程、图表、正常／异常情景及详情入口。结构与来源检查不能代替业务审阅。
3. 按 `schema --delivery` 保存同目录 `delivery-review.json`，使用 v3 绑定最终 documentHash；记录核心旅程、各功能当前 revision、状态判断、规则／依赖、验收映射及图表取舍。草稿有具体 reason 和 evidence，详细映射按 [内容审阅](content-review.md) 填写。
4. 运行 `document check /文档 --analysis-session SESSION --input delivery-review.json --json`；只有 `valid:true` 才称严格通过。漏读、漏记录、漏映射继续补齐；真实能力限制可在缺口完整可见、deliverable:true 时部分交付，不将其称为严格通过。
5. 按下节启动并核对本机编辑服务，打开页面。以上步骤均由 AI 内部执行，结果保存到相应记录，不要求用户验收或决定如何交付；最终回复按 SKILL.md 模板，只展示可编辑链接、产品定位与核心旅程。

若 JSON 已保存而 HTML 生成失败，仅运行 `render` 恢复，不重复新增或完成登记。源码在交付期间变化时重新核验，不用新指纹替换旧基线来消除提示。

## 启动可编辑页面

生成产品书及运行 `render` 不会自动启动服务。完整初始化默认包含启动本机编辑服务，无须用户再复制命令；只预览或用户明确要求静态交付时遵循其要求。

1. 使用当前已核对协议的 CLI，通过宿主支持的持久进程／后台任务运行以下命令。传入本次生成文档的绝对目录或 JSON 路径；在工具源码仓库可使用等价的 `pnpm blueprint serve`。

   ```sh
   product-blueprint serve /本次产品书的绝对目录 --port 0 --json
   ```

2. `--port 0` 让系统选择空闲端口；等待启动成功，读取输出的 `url` 和 `document`。不要拼接默认端口、复用其他项目地址或终止用户已有服务。已有服务只有确认仍在运行且指向同一文档时才复用。
3. 访问实际 `url` 的 `/document/capabilities`，确认 `canSave:true` 且 `documentPath` 指向本次权威产品 JSON，并确认首页正常返回。保存能力核对使用只读请求，不向用户文档写测试数据。
4. 用宿主可用的浏览器或页面打开能力打开该 `url`，已有同一网址的页面可复用，确认页面支持保存定义和批注。直接打开 `index.html` 是只读快照，不能替代此步骤。
5. 交付文字为“打开产品书（可编辑、可保存）”的 Markdown 链接，目标使用实际 `url`，并保持服务任务运行；不要在交付前清理它。服务退出后链接会失效，无法持续运行时说明这一限制，不声称编辑入口可用。

服务启动、能力核对或浏览器打开失败时，按 SKILL.md 分别说明实际结果；保留已生成文件，修复服务问题无需重新初始化。仅在用户要求静态交付或编辑服务暂不可用时提供绝对路径的只读 HTML 备用链接。

## 结束与恢复核对

文档交付检查通过、编辑服务与页面核对完成后，本次初始化即达到结束条件。若宿主已有对应的目标或计划，核对后将其标记完成，再按 SKILL.md 简短交付；没有目标时不为结束任务另建目标。保留服务进程，不把重复复核当作新的工作轮次。

收到恢复、重复触发或自动续跑通知时，先读取现有文档及绑定当前哈希的审阅记录，检查源码状态与服务保存能力。已有交付有效且任务没有新增要求时，不再执行 init、变更批次、完成登记或验收命令；必要时恢复编辑服务，然后结束对应目标并简短回复。发现文档、源码或服务失效时，仅补做使交付失效的相应工作；涉及现有用户内容的业务修改仍按维护边界处理。
