# 初始化图表交付

图表用于让人和 AI 理解产品如何运转。先建立业务定义与流程，再根据同一批源码分析或需求依据生成语义图表，固定模板负责布局。通过 CLI schema 获取字段结构，不为某个项目改写页面或嵌入 SVG。

## 逐项判断

- 功能时序图 `sequence`：参与者之间有操作、请求、响应或协作顺序时生成，说明谁在何时与谁交互。参与者可以是人、页面、服务、文件或外部工具；不要求存在网络服务。消息关联当前功能的真实步骤，有依据时区分正常与失败情景。单一参与者且没有值得说明的交互时可以跳过。
- 功能数据流图 `dataflow`：有输入、处理、转换、保存或输出时生成，展示数据对象如何经过处理形成结果。节点按数据、处理与存储区分；边标注传递的内容。不要仅把业务步骤改名后串成另一张流程图。
- 项目架构图 `diagrams.architecture`：已知角色、组成部分及职责边界时生成，说明谁使用什么、工具与外部系统如何协作。模型在外部运行时明确边界，不画成页面或 CLI 直接调用 AI。
- 项目数据关系图 `diagrams.entities`：有稳定业务对象及引用、包含或版本关系时生成，说明对象之间的关系。没有数据库也适用，例如文档、功能、步骤、依赖、定义版本和验收记录；不要将逻辑对象虚构成数据库表或字段。

图表范围服从真实依据。已有行为引用源码分析；需求情景引用用户或文档原文；无法确认的交互、数据转换和关系留作未知，不能画成已实现事实。源码调用目标未解析时不猜测内部路径；可使用有依据的职责边界表示交互。

填写 sequence.failure 时同时写实际 error 分支，不能只换情景名称后继续显示正常或公共消息。只读行为也可能有多方请求与响应，是否修改状态不作为省略时序的理由。跳过时引用另一图作为替代的，交付 decision.alternative 指向实际生成的图；不能声称“数据流图已表达”却也跳过数据流。架构关系应覆盖核心旅程中的阅读、输入、处理和输出职责。

## 保存与交付检查

1. 对每个功能判断时序与数据流，对项目判断架构与数据关系。缺失有理由：不适用或依据不足，写入对应功能 notes 或交付报告；保留已有备注，不覆盖用户内容。
2. 图表使用稳定节点编号、有效边引用和当前步骤编号；补充或重排流程后同步相关图表，不沿用失效步骤索引。依赖引用必须存在。
3. 按最终字段绑定 analysis trace，检查来源及字段值。图表字段在 Schema 中可选，也不作为完成登记必填，但初始化仍要执行覆盖判断；结构与分析检查通过不能替代这项检查。
4. 保存后用浏览器检查实际图表、正常／失败情景、节点或步骤详情，并检查窄屏时序列表与数据图阅读。只在确实缺失或不适用时接受空状态。
5. 将已生成及跳过的图表和原因写入产品书或交付审阅记录，不展开到默认成功回复。图表变化由现有版本规则管理；已有功能重新核验后登记当前版本，不直接改写版本或完成字段。
