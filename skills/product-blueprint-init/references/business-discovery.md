# 业务发现与核对

在首次建模或代码出现新入口时读取本页。业务能力由目标项目的使用者、目标和结果决定，不预设名称、数量或分组。

## 先建立操作清单

1. 读取产品介绍、包入口、配置及项目公开工作流；将 README、需求文档及相关配置显式纳入扫描 contexts，再运行 `analysis scan`。
2. 在全量详细记录之前分页读取 `business inventory --session SESSION`。它列出注册/分发身份、模块概览及上下文，尚未证明业务含义。
3. 对照实际页面动作、API、CLI子命令、事件、定时任务、公开库API和工作流反查入口。未知框架/动态路由要继续读其配置和调度源码；清单不能自动穷尽它们。

先看 `analysis capabilities` 的 `business.adapters` 与 `business.boundaries`。JS/TS、Python、Go、C++ 共用同一业务地图协议，但自动入口按框架声明：Python 有 Flask/FastAPI、Click 直接命令和 argv 分支；Go 有 net/http、argv 分支和并发调用候选；C++ 有显式 httplib Server 注册和 main argv 分支。Python 组件挂载、动态方法、跨文件 handler 及宏/模板包装等未知关系须沿原始配置和调用继续核对。服务注册不等于已经监听，候选不等于当前功能已实现。

同 handler 可以有多个操作，同 dispatcher 可以有多个命令。候选操作不是功能：导出 helper、开发脚本、健康检查可能只是支撑；产品本身将工具能力交付用户时也不能随意排除。候选的 certainty 不等于当前功能实现状态。

## 建立业务地图，再展开核对

先从三种视角各自列候选：使用者目标与结果；实际触发操作；业务对象、状态和规则。合并时不能把第一份摘要当成真值。

每个能力说明 actor、goal、outcome，关联 operationIds 和真实 results；纯需求可用 classification:requested、operationIds:[] 并引用 requirement 原文，不能冒充已有实现；document 需求须给当前 contextId 和匹配原文，user 来源仅限实际用户原话；读取 `schema --business` 获取当前字段。`business record --session SESSION --input 地图.json` 保存早期地图并返回遗漏。尚无依据的候选继续追查，不以 helper 名字或一段通用说明代替。地图是分析产物，不直接改写用户产品书。

逐能力沿入口追到结果，读取完整相关函数、调用邻域、规则、拒绝/异常与持久化。再按模块完整读取剩余自有函数，核对低关联模块及配置是否藏有遗漏业务。不要先为所有语法位置写长篇文字，再开始考虑用户做什么。

- 每个已识别操作归属能力或具体非业务分类；非业务理由写入 reason；source 必须完全等于 operation.registration.file 的相对路径，不附行号或说明，不删除原操作凑覆盖率。
- 每个能力须有真实触发和结果依据。状态查询、快照、哈希和结构校验器不能证明外部AI理解需求或修改代码。
- Skill/文档工作流结果须引用其指令原文，工具函数不能代替。指令存在与本次AI实际执行成功分别记录。
- 文档承诺逐项与源码核对，区分已有实现、未实现和待确认；README可能过期。
- 多个操作可以合成一个用户目标；独立目标可以有共享实现。不得用功能数量或强迫不同函数来判定业务正确。

## 完整阅读，减少重复说明

按文件使用 `analysis pack 文件相对路径 --session SESSION`，正文只输出一次，范围内函数/嵌套函数仍独立列出。长文件跟随 nextOffset 分段；使用工具真实 receipt 支持完整覆盖的单元，不自行写凭据或修改会话内部状态。

完整读包不等于所有函数已经分析。逐函数记录八项行为字段；推荐 claims：每个断言用 pointIds 关联一组因果相关位置，并用 detail 解释该真实语义。一个条件决定后续返回时可以合并解释，不必每个参数、调用写重复句子。每个 reviewPoint 仍恰好一次，嵌套函数有独立记录。旧 coverage 仍可读写，但不作为新工作流的首选。脚本只组装已理解的内容，不根据行号、语法种类或词库生成解释。

重新扫描后检查 reuse.records、reuse.invalidatedFiles 和 indexRebuilt，并运行 analysis check。相同快照不重建机器索引；新快照仅复用完整、合格且源码/位置/依赖未变的函数分析，记录保留 reusedFrom 和读取凭据出处。只补齐 pending；旧浅摘要、规则/上下文变化及受影响依赖不能复用。Go/C++ 等未知依赖按语言范围保守扩大，不为追求复用率缩小真实影响。业务地图、字段依据、流程与运行记录不随函数分析自动继承，仍要独立更新。不能手工复制凭据到新快照，也不能把工具复用描述成本轮 AI 重新阅读全文。

正文、已读取、语义记录、业务核对、运行验收分别记录。继续完成可解决的未读项；全仓索引不冒称完整理解，时间长不构成真实能力豁免。

## 独立核对与文档绑定

产品书定义稳定后，给各能力填写实际 featureIds，重新执行 `business record --document BOOK --session SESSION --input 地图.json`，绑定当前定义。定义或地图变化需重新核对。

运行 `business check BOOK --session SESSION` 查看操作遗漏、来源和版本绑定。coverageValid 核对操作、引用、定义绑定及入口到结果的真实源码路径；valid 还要求能力和排除项审阅完成。保存 business record 不是通过检查，读取 stage 和 pendingExclusions。仍不宣称机器证明自然语言正确。同一分派器的其他命令/else 分支，以及仅注册但未调用的回调，不能证明此操作结果。结果可用 operationIds 限定对应操作；静态关系未知时，可用 via:{flowId,scenarioId} 引用当前产品书和源码下已实际通过、精确断言结果位置的流程。库入口与有明确真值守卫的分支可用此证据；直接调用 handler 不证明 HTTP/事件注册已触发，未支持的边界继续保留未核验。

逐能力对原始入口、结果位置和工作流原文作语义审阅，用 `business review` 的 decisions 保存 supported、contradicted 或 unknown及具体原始依据。结果依据须指向实际结果；审阅还可引用条件、守卫等真实位置来核对结论。所有非业务分类也用 exclusions 逐操作引用其源码/上下文审阅，不能靠排除操作提高覆盖率；pendingExclusions 不为零时仍未审阅完成。条件允许时用独立上下文复核，向审阅者提供原始项目材料和地图，不给预设答案；对矛盾继续读源码。无独立复核能力时如实标记 reviewer来源，不编造另一个模型已确认。工具把审阅标为 agent-submitted，不宣称可信认证。

验收预期从业务规则/明确需求制定，再选择执行边界；不从某个容易探测的返回值倒推业务。保存后从独立路径读回内容和版本，失败后检查原数据/输入是否保留。少量关键断言使用受控反例核对：禁用保存或绕过冲突后，原验收应失败。共享helper允许，不以重复观察冒充多项业务结果。

新初始化使用 delivery v5。旧交付只保留原有范围，不能当作已完成新业务地图检查。业务地图、函数阅读和语义记录、功能实现状态、运行验收互不替代。

## 公开操作与排除

清单中的 requiresBusinessOwner 用于提醒公开 API、页面动作、命令、事件和工作流的业务归属。内部库导出可以按具体职责作 internal；公开操作应进入业务能力，或用 kind:support、capabilityIds 关联其实际源码结果。不能将页面/API/CLI 一律归到文档型 Skill 下。仅未确认的候选允许以 kind:false-positive 提交原始依据审阅，明确声明的操作不能这样排除。

排除说明与 review.exclusions 逐项对应，完整读取并分析被排除单元。不同职责复用一条通用理由会被拒绝。多个操作可以同属一个用户目标，也可以共享函数，不按数量判断业务；业务覆盖、实现状态和运行验收分别记录。

依赖的具体技术名称应核对 package 清单和真实 import；没有依据时保留未知，不凭常见技术栈补全。
